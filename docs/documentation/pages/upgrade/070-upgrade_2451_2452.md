# Upgrade v24.5.1-v24.5.2-rc.0

This page describes the required steps to upgrade your Astarte Operator from `v24.5.1` to
`v24.5.2-rc.0`. This is a maintenance release of the Operator, and it is compatible with Astarte `1.2.1`.

> [!NOTE]
> This is the first Operator version that is able to handle Astarte `1.2.1`.

In the following, the upgrade path is described.

The upcoming sections will cover the following topics:

- upgrading the Astarte Operator,

Before starting with the upgrade procedure it is strongly advised to [backup your Astarte
resources](095-advanced_operations.html#backup-your-astarte-resources).

## Upgrade Astarte Operator

The Astarte Operator upgrade procedure is handled by Helm.

The current section assumes that the Operator's chart landing version is `v24.5.2-rc.0`. It is **your
responsibility** referencing the proper `v24.5.2-rc.0` chart using the `--version` flag when running
`helm` commands.

Please, make sure that the values you set for both the Operator's name and namespace match the
naming you already adopted when installing the Operator. A wrong naming can lead to a malfunctioning
Astarte cluster.

For standard deployments the following variables should be ok. However, it is your responsibility
checking that the values you set are consistent with your setup:

```bash
export ASTARTE_OP_RELEASE_NAME=astarte-operator
export ASTARTE_OP_RELEASE_NAMESPACE=astarte-operator
export ASTARTE_OP_CHART_VERSION=24.5.2-rc.0
```

Update your local Helm charts:

```bash
helm repo update
```

To upgrade the Operator use the dedicated `helm upgrade` command:

```bash
helm upgrade $ASTARTE_OP_RELEASE_NAME astarte/astarte-operator -n $ASTARTE_OP_RELEASE_NAMESPACE \
  --version $ASTARTE_OP_CHART_VERSION
```

The optional `--version` switch allows to specify the version to upgrade to - when not specified,
the latest version will be fetched and used.

By design, Astarte Operator's Helm charts cannot univocally be mapped to Operator's releases in a
one-to-one relationship. However each chart is tied to a specific Operator's version, which is user
configurable.

Therefore, upgrading a chart leads to an Operator's upgrade if and only if the Operator's tag
referenced by the chart is changed. You can check the Operator's tag bound to the chart simply
running:

```bash
helm show values astarte/astarte-operator
```

As usual, you can use the `--version` flag to point to a specific chart version.

## New Clustering Configuration for Astarte 1.2.1

Astarte `1.2.1` introduces new environment variables to control clustering behavior, which are particularly important for deployments on AppEngine and DUP.

### Clustering Strategy Configuration

The new `CLUSTERING_STRATEGY` environment variable controls how the service discovers other nodes. The available options are:

- `none` (default): The service will not look for other nodes/services
- `docker-compose`: Work in our docker-compose environment and no additional configuration is needed
- `kubernetes`: Uses Kubernetes DNS to find other nodes/services (requires additional configuration)

### Kubernetes Clustering Variables

When using `CLUSTERING_STRATEGY=kubernetes`, the following additional environment variables become relevant:

#### General Kubernetes Configuration

- `CLUSTERING_KUBERNETES_NAMESPACE`: Specifies the namespace where the Astarte instance is deployed (defaults to `astarte`)

#### Data Updater Plant Configuration

- `DATA_UPDATER_PLANT_CLUSTERING_KUBERNETES_SELECTOR`: The Endpoint label to query for other data updater plant instances (defaults to `app=astarte-data-updater-plant`)

#### VerneMQ Configuration

- `VERNEMQ_CLUSTERING_KUBERNETES_SELECTOR`: The Pod label to query Kubernetes for VerneMQ instances (defaults to `app=astarte-vernemq`)
- `VERNEMQ_CLUSTERING_KUBERNETES_SERVICE_NAME`: The Service name to query Kubernetes for VerneMQ instances (defaults to `astarte-vernemq`)

### Configuration Example

For Kubernetes deployments, you might configure these variables in your Astarte custom resource:

```yaml
apiVersion: api.astarte-platform.org/v1alpha3
kind: Astarte
metadata:
  name: astarte
spec:
  # ... other configuration
  components:
    dataUpdaterPlant:
      additionalEnv:
        - name: CLUSTERING_STRATEGY
          value: "kubernetes"
        - name: CLUSTERING_KUBERNETES_NAMESPACE
          value: "your-astarte-namespace"
        - name: DATA_UPDATER_PLANT_CLUSTERING_KUBERNETES_SELECTOR
          value: "app=astarte-data-updater-plant"
  vernemq:
    additionalEnv:
      - name: CLUSTERING_STRATEGY
        value: "kubernetes"
      - name: CLUSTERING_KUBERNETES_NAMESPACE
        value: "your-astarte-namespace"
      - name: VERNEMQ_CLUSTERING_KUBERNETES_SELECTOR
        value: "app=astarte-vernemq"
      - name: VERNEMQ_CLUSTERING_KUBERNETES_SERVICE_NAME
        value: "astarte-vernemq"
```

> [!IMPORTANT]
> These clustering variables are essential for proper operation in distributed environments like AppEngine. Ensure you configure them according to your deployment strategy before upgrading to Astarte `1.2.1`.

## Upgrade Astarte to Version 1.2.1

After upgrading the Operator, you can proceed with upgrading your Astarte instance to version `1.2.1`. Make sure to review and configure the new clustering environment variables as described above before performing the upgrade.

The upgrade process will automatically handle the deployment of the new clustering configuration once the environment variables are properly set in your Astarte custom resource.
